# 通用开发执行协议

> 适用于用户已手动完成需求澄清、技术选型、PRD/验收标准和原型设计的新项目；本流程从架构设计开始。用户当前明确指令和项目专属规则优先；项目已有同等职责规则时合并。每项任务开始前读取本文件和当前任务入口。

## 1. 文档职责和真源

| 问题 | 真源 |
| --- | --- |
| 当前实际行为 | 当前代码、配置、迁移和本轮可核对的验证证据 |
| 目标、业务范围、验收 | 用户已确认的需求、PRD/验收标准和原型；spec 只细化执行 |
| 技术边界 | 用户已确认的技术选型、通过后的架构及项目编码规范 |
| 顺序、依赖、停止点 | 基架完成后形成的开发计划；架构通过前以本协议的入口顺序为准 |
| 当前导航 | `docs/README.md`，只摘要和链接，不复制验收结果 |
| 执行结果、审查、恢复 | 当前功能或工作包的 spec；复杂跨工作包现场才另补一份交接 |

在 `docs/README.md` 填真实路径和版本；实际文件未提供时写“未提供”，不要编造。代码说明“现在是什么”，不能自动改写“应该是什么”。计划/spec 与代码冲突时先给出证据；原意明确且已授权的缺陷按原意修复，实质业务取舍交用户决定。

## 2. 接入顺序与架构确认

1. 先核对四份用户手动完成的资料及现有代码，在 `docs/README.md` 登记路径、版本和影响架构的冲突；不重新做需求澄清、技术选型、PRD 或原型。
2. 使用 `docs/architecture/_template.md` 或项目已有等效文档，设计系统边界、前后端模块、数据/API 契约、安全与失败路径，写清基础架构交付和验收。向用户提交具体版本；**收到用户针对该版本明确回复“通过”之前，不搭建或修改前后端基础架构代码，也不进入功能开发**。一般的“继续”“自动完成”不代替本检查点。版本变化影响已通过架构时，提交差异并重新取得受影响方案的确认。
3. 架构通过后，建立/沿用基础架构工作包 spec，核对现有基架；按获批架构搭建缺失的前后端基础和可运行、可测试入口，验证并独立审查。已有合格基架直接记录复用证据，不机械重建。
4. 基础架构工作包验证与独立审查通过后，使用 `docs/plans/_template.md` 或等效计划，从 PRD 验收项、原型、获批架构和实际代码拆出大阶段、工作包及小任务。每项有可观察输出、验收、依赖和风险；建立验收项到任务的覆盖映射，不把联调、迁移或阶段集成遗漏。计划细化已批准范围时直接继续；新增业务决定或架构变化交用户裁决。
5. 按计划和依赖进入下文开发循环；所有阶段、任务状态与下一步在 `docs/README.md` 导航，并以计划/spec 的实际记录为准。

## 3. 授权与任务入口

- 只读分析、解释、审查：只报告结论，默认不改文件。用户授权的文档维护在范围内直接完成，并核对链接、术语和差异。
- 架构获用户明确‘通过’后的基础架构，以及从已确认资料拆出的计划内工作包：核对依据、依赖、目标、非目标、验收和停止点后实施；已有批准持续有效，不因拆成步骤重复请求确认。资料只写标题而不足以确定业务结果时，指出具体缺口。
- 新增功能、改变业务契约、扩大范围或改变已确认架构：先把具体方案和验收写入 draft spec，取得用户对新增部分的明确批准，再实施。普通、可逆的实现细节在批准范围内自行决定。
- 高风险决定由用户介入：删除数据、破坏性或改变数据语义的迁移、超出已批准范围的迁移、认证授权或安全边界变化、对外发送/发布、费用、不可逆操作，以及不能从已确认材料推断的业务取舍。已批准范围内的常规迁移按计划执行并在独立测试库验证，不重复请求许可。记录需要裁决事项的选项、影响、建议、用户决定及依据；等待时继续独立的已授权工作。
- 提交、合并、部署和对外发布分别遵守项目授权；实现授权不自动等于生产发布授权。用户指定的阶段停止点必须遵守。

## 4. 开发循环

1. 基础架构和每个功能工作包各用一份 spec，内部按有独立验收边界的任务 ID 记录执行。小修复写入所属功能的原 spec；不要为每次编辑或每条测试另建 spec。读取当前 spec、已存在的计划相关部分、获批架构、项目规范及相关实现和调用方；基础架构工作包尚无开发计划时以获批架构为准。核对工作区现有改动、分支/基线；无 Git 时记录“无 Git 基线”，不编造提交号。
2. 开始任务前核对前置任务已 `verified`、必要输入可取得、验收项有对应验证方式，以及授权和停止点。用与任务规模相称的几句话说明目标、允许改动范围、非目标、风险和验收。条件不满足时记录阻塞，只暂停受影响任务。
3. 在同一 spec 中建立验收项与验证方式的对应关系；按依赖实施。保留他人改动，只做任务相关修改，复用现有实现与依赖；新增依赖说明必要性。不能以简化为由略过必要的安全、错误处理或数据一致性。
4. 修改后检查最终差异和受影响调用路径。失败先分类、保留原结果，再依据新证据在授权范围内修复并重验；不得通过删除检查、弱化断言或修改规格掩盖实现偏差。
5. 在当前 spec 的任务记录中写实际变更、证据、失败经过、独立审查、偏差、未验证项和下一步。代码实现完成但验证或审查不足时，该任务为 `implemented`，不能标 `verified`。

## 5. 验证与证据

测试分层、触发时机、慢测、环境隔离与失败复验按 `docs/testing-mode.md` 执行；项目真实命令由 `docs/development.md` 维护。实施前把验收项映射到检查；开发循环优先运行受影响检查，大阶段完成、合并或发布前运行受影响端完整检查；风险或共享调用范围扩大时扩大验证。

| 改动 | 至少核对 |
| --- | --- |
| 文档 | 差异、受影响链接、术语和规则一致性 |
| 单模块代码 | 相关静态检查、针对性测试及正常/错误/边界路径 |
| UI | 相关检查、实际交互和关键尺寸；纯单元测试不替代浏览器核对 |
| 共享接口、认证、权限、任务、外部副作用 | 受影响调用方、集成边界与专项失败路径 |
| 数据库迁移 | 独立测试库首次建库、旧版本升级及必要的数据结果 |
| 依赖、构建、部署 | 安装/锁文件、构建、启动或冒烟路径，按影响范围执行 |

每条证据写明选择理由、命令或操作、日期、代码基线、耗时、结果和报告位置；延期项写明归属的后续检查时机。环境错误与业务失败分别记；失败后单独复跑通过不能抹去原失败。未运行的必要验证写原因、影响及后续动作。模拟服务、mock 或文档演练不能写成真实外部链路通过。后续代码改变使证据失效时重跑受影响检查。不得把旧窗口、历史 checkpoint 或测试数量当作本轮证明。

失败按环境/依赖、输入或需求不清、实现缺陷、测试缺陷、架构缺陷、权限或外部系统分类。在任务记录中保留失败检查、稳定的错误特征（错误码、归一化信息、相关路径或接口）、每次尝试的结果及下一次尝试依据；换窗口不清空。同一失败重复且没有新证据或可检验的修复思路时停止盲目重试，说明阻塞；权限、数据损失、不可逆操作或范围争议出现时立即停止受影响部分。这里不规定机械的固定重试次数。

## 6. 独立审查和完成条件

每项变更任务完成开发与本轮验证后，交独立窗口或未参与实现的审查人；可自动开窗时使用独立窗口，否则使用根目录 `README.md` 的可复制指令。作者的自查只用于送审前准备，不冒充独立审查。

审查者核对批准范围、最终差异、已有改动、验收证据、错误/边界路径、风险和未验证项，并给出“通过 / 需修改 / 无法判定”及依据。审查结论要绑定任务 ID、实际改动范围和当时的代码基线；开发窗口把结论记入**同一 spec 的对应任务记录**。需要修改则修复、重验、再审；审查后若代码变化影响原结论，重跑相关检查并重新审查受影响部分。没有真实审查结论时不得标 `verified`；审查无法执行时记录原因和可复制指令，保持 `implemented`。

spec 与其中任务使用 `draft → approved → implemented → verified` 表示进度；`draft` 仅用于尚待批准的新决定，获批架构内的基础架构任务及从已确认资料拆出的计划任务直接按批准范围执行。阻塞、失败和中断写在任务记录及恢复区，不冒充完成状态。每项任务只有适用验收和独立审查均通过，且最终代码仍与证据一致，才标 `verified`；整个 spec 还须所有必需任务和整体验收通过才能标 `verified`。`verified`、提交、合并、部署分别记录，不能互相替代。

## 7. 阶段、交接和恢复

架构通过且基架完成后形成的开发计划维护 Phase → 工作包 → Task、顺序、依赖、验收覆盖与停止点；任务的执行细节仍在 spec。进入依赖工作包前，核对前置任务和整体验收已 `verified`，以及未解决风险和停止点；不能因“代码已写完”越过前置条件。阶段完成时核对所有相关任务与集成路径、运行阶段必需检查，更新 `docs/README.md` 的摘要和下一步。

日常换窗口以当前 spec 的恢复入口为交接：下一步、未验证项、失败历史、代码基线、现有改动和证据位置。仅跨多个工作包或现场复杂到 spec 无法清楚表达时，另补一份交接并引用原证据，不复制整套结果。旧计划、checkpoint 和历史会话只作线索。

新窗口先核对规则、已确认文档、当前代码、已有改动和证据；对照 spec 的状态与下一步。证据缺失、代码已变或记录过时时，先修正记录并重验必要项，再继续。待用户决定和停止点不因换窗口消失。

## 8. 交付

说明实际改动、验收与审查证据、运行或复验方式、未验证事项、下一步及提交/部署状态。发布按项目已有流程和授权执行；未配置外部服务或未取得费用授权时，不宣称真实集成完成。
