# 通用开发执行模板

适用于你已手动完成**需求澄清、技术选型、PRD 与验收标准、原型设计**的新项目。开发助手从架构设计接手：先交付可审阅的架构方案；你明确回复“通过”后，再搭建前后端基础架构，依据已确认资料和实际基架拆分开发阶段、工作包与小任务，随后逐项开发、验证、审查和交接。本模板不重做前四步，不配置模型或特定开发软件。

## 放进项目

先查看目标项目已有规则、代码、文档和未提交改动，再按需合并本目录文件；不要直接覆盖已有 `AGENTS.md`、架构、计划或 spec。项目有同等职责文件时，沿用并补足缺失规则。文件用途见 `文件使用指南.md`。

| 顺序 | 执行动作 | 记录位置与停止条件 |
| --- | --- | --- |
| 1. 接入 | 填写四份已确认资料的真实路径、版本和项目现状；核对它们的冲突与缺口 | `docs/README.md`；影响架构的缺口先请你裁决 |
| 2. 架构设计 | 基于 PRD、原型、技术选型和现有代码形成架构、模块/数据/API 契约、风险及基础架构验收方案 | 用 `docs/architecture/_template.md` 形成项目架构文档，交你审阅；**收到你对该版本明确回复“通过”之前停止代码搭建** |
| 3. 基础架构 | 按获批架构搭建前后端项目骨架和必要的运行、测试、接口基础；沿用现有项目结构 | 用 `docs/specs/_template.md` 记录基础架构工作包，完成验证及独立审查后再拆任务 |
| 4. 拆任务 | 对照 PRD 验收项、原型、获批架构和实际基架，拆成开发阶段 → 工作包 → 可独立验收的小任务；确定顺序、依赖、风险、验证和阶段停止点 | 用 `docs/plans/_template.md` 形成项目计划；逐项检查需求覆盖和可执行性，不新增未批准需求 |
| 5. 开发 | 按计划为工作包建立/沿用 spec，逐项实施、选测、验收、独立审查；依赖任务通过后继续 | 结果和下一步写同一 spec；阶段集成按 `docs/testing-mode.md` 执行 |

这里的“通过”是架构版本的明确人工确认，不要求对每个小任务重复确认。架构确认后若拆任务发现重大业务取舍、架构变化、费用或不可逆风险，只暂停受影响部分，给出证据和选项请你决定；已批准且独立的工作继续。项目已有合格基架时，先核对是否满足获批架构与验收，再记录复用结果，不机械重建。

## 可复制的独立审查指令

每项变更任务完成开发与必要验证后，交独立窗口或未参与实现的审查人。开发软件无法自动开窗时，复制下文到另一个窗口。没有真实审查结论时任务保持 `implemented`。

```text
请独立审查本项目当前任务。你没有参与实现；先读 AGENTS.md、docs/README.md、当前工作包 spec 中的任务 ID、获批架构、开发计划及相关已确认资料。核对实际代码差异、代码基线、已有改动、验收项和可获取的验证证据；检查适用的正常、边界、错误、权限和受影响调用路径。不要以开发者完成声明代替证据，不修改代码或状态文件。请返回：任务 ID、代码基线与改动范围、结论（通过/需修改/无法判定）、逐项发现及文件位置、已核验的证据、未验证项、建议的下一步。开发窗口把结果写回同一 spec。
```

## 纸面示例

假设已确认 PRD 要求“导出空数据时返回约定空文件”，原型给出了入口。助手先形成架构方案，写明导出接口、数据流和错误处理，交你审阅；收到该版本“通过”后核对或搭建前后端基架。随后在计划中建立阶段 `P-01`、工作包 `W-01` 和小任务 `T-01`（空数据导出）、`T-02`（依赖 `T-01` 的页面联调），把验收项映射到任务。`T-01` 开发与检查完成后由独立窗口审查；审查或验证未通过就修复、重验、再审。`T-01` 为 `verified` 后才能推进依赖它的 `T-02`。换窗口时，新助手先核对实际代码和证据，再从记录的下一步继续。

这是流程演练，未实际验证任何开发软件的自动开窗、后台调度、自动审查或项目运行能力。
