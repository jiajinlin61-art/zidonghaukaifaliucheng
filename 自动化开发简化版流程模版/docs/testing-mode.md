# 分层测试模式

> 适用于架构获用户明确‘通过’后的基础架构搭建、任务拆分后的开发执行。测试选择属于任务实施，不重新设计需求或验收标准。`AGENTS.md` 规定完成条件；本文件规定何时测、测什么和怎样处理慢测；`docs/development.md` 只填本项目真实命令；本次运行结果只写当前 spec。

## 1. 目标与边界

- 让一次相关改动尽早得到有效反馈；把昂贵的全量、真实外部链路和人工检查放在它们能判断阶段结果的位置。
- 节省等待时间不能靠弱化断言、跳过必需风险路径、用模拟结果冒充真实验收，或把失败的全量运行写成通过。
- 不要求每次保存文件都测试；以一组能独立判断结果的改动为最小开发检查单位。已验证且代码、配置及依赖未改变的结果不重复运行。
- 基础架构的验收边界以获批架构和对应 spec 为准；后续任务以拆分后的计划和 spec 为准。确需真实端到端或人工验收时，可以在**事先明确的独立集成任务**完成；前一任务只对其自身已定义的范围标 `verified`，不能暗中把未验证项算作已通过。

## 2. 新项目开始时填写一次

1. 在 `docs/development.md` 登记真实可用的检查命令、运行目录、前置服务、测试数据隔离和外部费用边界。没有可执行命令就标“待配置”，不填猜测的命令。
2. 按代码调用关系建立“改动范围 → 受影响测试”的最小映射，先用已有测试文件或测试名；测试分类标记只有在覆盖完整、含义核实后才用作自动筛选。未标记的集成测试不能被误当快测。
3. 区分纯逻辑测试、需要本地/独立数据库或服务的集成测试、真实第三方链路、浏览器或人工验收。记录哪些测试有清库、共享状态、网络、费用或不可逆副作用。
4. 需要测量性能时，先在安全测试环境做一次基线统计：总耗时、最慢用例、启动/清理/外部等待、失败类型。不要从一次异常慢跑直接推定根因或据此删除测试。

已有项目沿用其测试工具与环境，不因采用本模式更换框架、解释器或数据库。项目没有阶段划分时，最终交付任务承担阶段集成检查。

## 3. 四个检查时机

| 时机 | 触发 | 最小检查 | 结束条件 |
| --- | --- | --- | --- |
| 开发反馈 | 一组相关改动形成可检查结果后 | 最直接的静态或纯逻辑检查、针对性测试；先跑便宜且稳定的检查 | 发现问题后修复；这一步单独不代表任务验收 |
| 任务验收 | 任务实现完成、准备独立审查时 | 验收项对应测试、受影响调用方及风险专项；适用的 UI 实际交互、数据库或外部副作用检查 | 必需检查有有效证据；未验证项明确归属，审查者可核对最终差异 |
| 阶段集成 | 工作包/阶段收尾，或多个任务汇合 | 该阶段受影响端的完整静态与测试检查、跨模块路径、迁移或恢复检查、必要的人工验收 | 前置任务通过，集成结果绑定最终候选代码；失败不能以“基本完成”越过 |
| 合并/发布 | 确有合并或发布任务且获得相应授权 | 按项目规则确认最终代码的完整检查、构建、测试环境冒烟及必要真实链路 | 验收、提交、合并、部署分别记录；未执行的外部/生产验证不得声称通过 |

同一任务内有多个小改动时不机械重复任务验收；一次完整检查结果仅在对应代码与环境状态仍适用时复用。阶段检查后若又有代码变化，先判断受影响路径并重跑失效检查；无法证明完整结论仍有效时，在最终候选上重新取得完整结果。纯文档改动通常只需文档核验，除非改动了可执行契约、配置或验收规则。

## 4. 按改动选择检查

| 改动范围 | 开发反馈优先项 | 任务验收至少补齐 | 阶段/交付关注 |
| --- | --- | --- | --- |
| 纯逻辑、映射、格式化 | 对应纯单测与局部静态检查 | 正常、错误、边界及受影响调用方 | 所属端完整检查 |
| API、数据库读写、共享契约 | 对应服务/契约测试 | 独立测试库中的真实事务、权限、异常和调用方测试 | 跨模块集成与所属端完整检查 |
| 迁移、认证、授权、任务恢复、并发 | 直接命中的专项回归 | 首次建库/升级或重启/并发/越权等适用场景；必要的前后端契约检查 | 相关恢复与集成路径；高风险缺项不得无说明地延后 |
| 文件存储、供应商调用、其他外部副作用 | 可重复的隔离或替身测试 | 失败分类、超时、幂等、补偿与权限；按已确认任务边界运行真实集成 | 已获授权的真实链路及资源清理；替身结果单列 |
| UI、交互、视觉 | 受影响组件或状态测试 | 实际浏览器中的关键交互、错误态和适用尺寸 | 完整前端检查及业务链路走查 |
| 依赖、构建、部署配置 | 配置与锁文件核对 | 安装、构建、启动或相关冒烟 | 测试环境部署/恢复，按授权进入发布检查 |
| 文档、注释 | 差异、链接与术语 | 受影响的规则、路径或命令一致性 | 无代码行为影响时不因文档更新重跑全量 |

这里只规定选择原则。具体测试文件、命令和运行前提写在项目 `docs/development.md` 或现有等效文件。无法可靠界定影响范围时扩大到受影响端的完整检查，不以“只改一行”缩小风险范围。

## 5. 慢测、环境与并行

- 先找耗时来源：测试用例、测试环境启动与清理、数据库、网络、外部服务、浏览器等待分别计量。以多次结果区分稳定慢与偶发抖动，不设未经测量的硬性分钟门槛。
- 开发反馈优先使用无外部依赖的测试；需要真实数据库或存储的检查在相关任务验收时运行。慢测不自动等于可跳过，其执行时机由风险和验收决定。
- 测试数据库、对象存储和其他共享资源必须与生产及开发真实数据隔离。破坏性清理先由测试环境的硬守卫限制目标；缺少可信隔离时停止该检查并记录原因，不对生产或未确认资源试跑。
- 有共享清库、固定账号、后台任务或同一对象 key 的测试，不直接并行。只有每个并发单元具备独立资源并验证无互扰后才考虑并行。
- 测试运行中先确认进程与输出状态，不因等待久或回执不完整就重复启动。外部服务未配置、凭据无权或费用未授权时，用隔离测试继续可独立工作；真实链路标为未验证并保留独立验收入口。
- 优化测试初始化、清理或环境之前，先保存基线与隔离契约；优化后用正常、错误、清理、重启及重复运行检查证明没有削弱测试有效性。不要为提速随意扩大共享状态或关闭清理。

## 6. 失败、复验和证据

失败先区分业务断言、环境/依赖、测试自身、输入/需求或外部系统。保留第一次失败的命令、代码状态、错误特征和日志位置；修复后重跑失败项及受影响回归。单项复跑通过不能把先前失败的全量运行改写为“单次全绿”；阶段或交付需要完整检查时，须重新取得有效的完整结果。相同失败反复出现而无新证据或可检验修复思路时，按 `AGENTS.md` 停止盲目重试。

每次任务只在当前 spec 记录：任务 ID、改动范围、选择了哪些检查及理由、未选/延期检查归属哪个后续检查时机、运行日期与代码基线、命令/操作及环境、耗时、退出结果、失败与复验、证据位置。没有 Git 时明确“无 Git 基线”并描述文件差异。审查者核对“选择是否覆盖验收与风险”，而不只看通过数量；审查后影响结论的代码变更按规则重验和再审。

换窗口时先核对代码、现有改动和证据是否仍适用，保留未决外部验收、环境失败及失败历史；从 spec 的下一步继续，不凭旧窗口结论直接跳过检查。

## 7. 在新项目中持续改进

先在项目 spec 中记录实际耗时、重复等待、漏测、误报、环境故障和改进建议，不为每次测试另建日志。阶段结束时只总结有证据的重复问题：原检查何时运行、耗时和失败原因、拟调整的触发时机或环境、保留的验收覆盖、复验结果。单次慢测不直接上升为公共规则；确认可复用后，再按用户授权修订本模板。

## 8. 纸面演练

假设任务 A 修改纯映射逻辑，任务 B 依赖 A 并接入数据库，阶段末需要真实外部服务。A 开发时跑映射单测，任务验收时核对其边界与调用方，独立审查通过后才标 `verified`。B 开发时跑相关逻辑测试，任务验收在独立测试库检查事务与错误路径。外部真实链路若已在计划中属于阶段集成任务，A/B 的 spec 写明该边界；阶段集成完成前不得宣称真实端到端通过。若 B 全量测试遇数据库连接中断，保留失败事实，分类排查；单项复跑通过不能代替有效的阶段完整结果。新窗口先核对最终代码和这些证据再继续。

本演练只检查规则逻辑，不代表某个项目或开发软件已实际运行上述测试。
